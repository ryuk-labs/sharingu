# The gate, the suites, the ship, the migrations

The process (one sprint branch, slices, one review) is `AGENTS.md` at the repo root; the engine's layout is
`CLAUDE.md`. This file is the detail of the four steps every change passes. Counts are never typed into a doc: every
suite prints its own totals and the gate its own steps.

## The gate — `sh gate.sh`

Local and fast: no deploy, no live call. Its header lists every step (syntax, route orphans, MCP parity, the brand
gate, the code atlas, boot-schema coverage, the contract diff, the selftests, a wrangler dry-run build). Read it by EXIT
CODE, never through a pipe. Each run records itself in `.runs/gate.json`. `check-brand.py` is permanent: no tenant
fact, person name or record id typed into render output or a tool description; thread the seam (`src/tenant.js`).

## The suites — `sh evals.sh` · `sh sims.sh` · `sh tools/tabs-verify.sh` · `sh tools/verify-live.sh`

They curl a running worker over HTTP, never import its code. By default each starts a fresh local org as the smoke
does (`tools/lib.sh`: org `ryuklabs-local` under `tools/r-local.sh`, the fixtures of
`tools/suites/fixtures/` filed through `preview` → `file`; no Cloudflare request); `--live` targets the ryuklabs
worker and runs `tools/cf-budget.sh` first.
Never edit `evals.sh` or `sims.sh` while a run is in flight: `sh` reads the script as it goes, and the run dies on a
bogus syntax error.

## The ship — `sh tools/ship.sh ryuklabs`

Credentials first: `set -a; . ~/.sharingu/env-sharingu.sh; set +a` (a bare `wrangler` hangs on a login prompt). In
order: the gate by exit code → `tools/cf-budget.sh` → the live deployment must be ONE version at 100% (the rollback
target) → `wrangler versions upload` (a new version and its preview URL, no traffic) → a smoke on the preview (`/health`
must name the new version; `/home`, `/build`, `/decisions` on a minted seat) → `SHIP_PREVIEW_HOOK`, if set (the import
runs here: `SHIP_PREVIEW_HOOK='sh tools/import-live.sh'`) → 10% → the smoke, pinned to the new version → 100% → the
smoke again → `wrangler triggers deploy` (crons). A failed preview smoke stops before any traffic moves; a failure after
traffic moved rolls back and reads the live deployment back to prove it. `tools/ship-selftest.sh` (a gate step) walks
the whole ritual offline against a stubbed wrangler.

Undo: `sh tools/ship.sh rollback [<version-id>]`. A rollback restores CODE only; D1 is untouched. A brand-new org's
first deploy is plain `wrangler deploy` (`tools/new-org.sh`).

## Migrations

`migrate-0NN.sql` files are additive and applied by hand, never as a side effect of an edit and never by `ship.sh`:

1. rehearse: `sh tools/migrate-dryrun.sh ryuklabs-agent-r --from <NNN>` (NNN: the first pending migration's three digits) (replays the pending
   migrations on a local copy of the live data; read-only on remote; `sh tools/ship-plan.sh ryuklabs` names them);
2. apply: `sh tools/migrate.sh migrate-0NN.sql`. It runs the budget guard, reads a D1 Time Travel bookmark FIRST (no
   bookmark, nothing applied; the bookmark is appended to `.runs/migrate.jsonl`), prints the exact
   `wrangler d1 time-travel restore ryuklabs-agent-r --bookmark=<b>` that undoes it, and only then applies the file.

A restore returns the WHOLE database to that moment: every write after it is lost, not only the migration's. It is the
last resort; the first is a forward migration. `boot.sql` is the fresh-org schema, GENERATED by
`tools/export-boot-schema.sh`; `tools/check-boot-schema.py` (a gate step) fails when a migration is missing from it.
`schema.sql` is a commented reference, never applied. Treat `wrangler.jsonc` and `wrangler.tenant.template.jsonc`
(bindings, ids, crons) with the same care.

**Expand / contract (two versions share ONE schema).** A gradual deploy runs the old and the new worker side by side
(10%, then 100%), and a rollback puts the old one back on a schema the new one may already have migrated —
`wrangler rollback` never touches D1. So every schema change is split so that BOTH versions work at every moment:

1. **Expand** (a migration, applied BEFORE the code that needs it ships): only additions the old code ignores — a new
   table, a new NULLable column or one with a DEFAULT, a new index. Never a rename, a drop, a NOT NULL without a
   default, or a tightened CHECK in the same step.
2. **Ship** the code that writes and reads the new shape (`tools/ship.sh`), tolerant of rows that predate it; a
   backfill, if any, is its own idempotent migration.
3. **Contract** (a LATER migration, only once no live version reads the old shape — after 100% and after the rollback
   window): drop the old column or table, tighten the constraint.

A rename is expand (add the new) → ship (write both, read the new) → contract (drop the old), never one
`ALTER TABLE … RENAME`. The rollback target must still run against every schema the ship could have left behind; if it
cannot, the change was not split far enough.
